# 0.8 数据格式与迁移

0.8 将 `state.json`、明文导出和加密备份中的配置内容标为 `format: 4`。目前格式 4 仍使用单文件保存配置、数据加密密钥、历史快照、事件、保留数量和核心选择；版本号是兼容性边界。0.7.1.22 和 0.7.1.23 的本地加载和导入逻辑不接受格式 4；不要把格式 4 手工改成 3 或用旧程序覆盖它。更早版本的行为未在此处作保证。

首次加载格式 1、2 或 3 时，工作台读取并验证当前状态、每个历史状态和其中的加密密钥，确认没有当前程序不认识的字段，然后才升级。格式 1、2 使用原来的独立 `master.key`；格式 2 的历史快照从原 `snapshots` 目录读取。转换后的格式 4 保留这些状态、快照和原数据密钥；格式 1 如果没有保留数量字段，就至少保留全部已有快照，有字段时保留其有效值。已有的核心选择继续使用原有启动迁移逻辑。

替换 `state.json` 前，程序会在同一数据目录写入并回读核对 `state.before-format-4-from-<旧格式>-<随机值>.json`，然后才提交新状态。该文件是原始状态文件的字节副本；格式 1、2 的 `master.key` 和 `snapshots` 原件也会留在原处，不再由状态保存代码自动删除。如果写入副本或迁移前验证失败，原始 `state.json` 保持原样；如果新状态写入失败，原始副本和旧式独立文件仍保留。状态文件缺失但发现旧密钥、旧快照目录或迁移副本时，程序拒绝初始化空配置。

迁移副本包含敏感配置；格式 3 副本还包含数据密钥，应按凭据保护。格式 1、2 的副本依赖保留下来的独立密钥及可能存在的快照文件；其他安装数据和核心程序不包含在副本中。副本只反映升级前状态，不包含升级后的更改，不代表已经验证过完整回滚。建议升级前另行制作受保护的完整备份，并在排查故障时保留所有相关文件。

程序先同步副本文件，在支持的非 Windows 平台还同步其目录，再替换当前状态；Windows 目录项及异常断电后的持久性取决于系统和文件系统。不要将该流程视为跨多进程或多主机的事务。

明文导入和加密备份恢复接受格式 3、4 的单文件配置，并在验证后保存为格式 4；原导入文件不会被修改。无法识别的格式、字段或协议会被拒绝，避免程序忽略后写回丢失；迁移报错时应先保留原文件再排查。格式 1、2 的多文件数据只能通过原数据目录升级，不能直接作为单文件导入。原加密备份外层格式及密码算法保持不变，解密后的配置格式仍需检查。

导入前须停止全部实例并等待自动恢复和实例操作结束。为保持浏览器数值精度，导入会保留各历史快照的修订号，并根据本机当前修订和导入的快照分配新的当前修订号。为后续修改保留足够空间，导入快照的修订号不能超过 `2^52−1`；超过时会拒绝导入并保留原文件。磁盘中超过 `2^53−1` 的修订也会拒绝读取，不会改写原数据。

## 后续 0.8 功能的衔接

- 新增协议字段已纳入格式 4。当前界面尚不能编辑新协议类型，旧界面不能把这些规则改成其他类型；不表示已验证协议互通。
- 新增节点、Webhook 等数据时，需要同步扩展持久结构、验证和密钥处理。未知字段会使当前实现拒绝加载，而不会自动保留或实现这些功能。
- 新字段如果属于快照范围，还需同步更新 `State.clone`、公开视图、备份复制、保存和恢复路径；编辑表单及 API 必须保留用户未修改的字段。对格式 3 的旧字段保持原有含义和默认行为。
- 后续出现旧格式 4 程序不能安全理解的语义变化时，应再次升级格式或确保旧程序能明确拒绝，不应依赖旧程序忽略字段。合并并发行前还需在允许验证的环境中检查真实旧数据、异常中断及降级行为。
